# グラフィック・操作性改善 概要計画

関連する正本：

- ゲームの目的、画面構成、世界表現：[game-design-requirements.md](./game-design-requirements.md)
- 後半物流を含む人手確認項目：[phase6-human-playtest.md](./phase6-human-playtest.md)

本書は上記を置き換えず、グラフィックと操作性を改善する実施順序を定める。

## 1. 目的

既存のゲームルールとシミュレーションを維持したまま、次の状態を実現する。

- 初見でも、操作できる対象と次の一手が分かる。
- 採掘から地上搬送までの因果関係を、画面上の変化として追える。
- 暗い坑道の雰囲気を保ちながら、背景・設備・キャラクター・運搬物を判別できる。
- HUDに頼りすぎず、世界内の設備やアニメーションを主要な状態表示にする。
- 現在の図形中心の描画を画像素材中心へ段階的に移行し、深度や設備の視覚的な個性を強める。

本計画は実装の概要と順序を決めるものである。個別の色、画像寸法、アニメーション枚数、文言、入力仕様などは各段階の着手時に決定する。

## 2. 対象範囲

今回扱う改善は以下の6項目とする。

1. クリック可能な物の識別
2. 次に行う操作の一手単位の案内
3. 暗部と操作対象の階調整理
4. 行動結果の視覚・音響フィードバック強化
5. HUDの情報階層整理
6. 設備・鉱脈・人物のシルエット改善と画像素材への移行

現在Canvasの図形で表現している世界グラフィックは、動的な補助表示を除き、画像素材中心へ移行する対象に含める。モバイル専用レイアウト、新しい深度固有ランドマークの追加、ゲームバランス変更、コンテンツ追加は今回の直接の対象外とする。ただし、画像素材の設計では将来の深度固有表現を追加できる構成を維持する。

## 3. 維持する設計原則

- ゲーム状態が描画を決める。状態と無関係な作業・運搬アニメーションは追加しない。
- 画面に見える物流を、HUD上の数値だけで置き換えない。
- 操作対象の見た目とクリック判定を分離し、素材差し替えで操作範囲が不安定にならないようにする。
- 重要な状態は色だけに依存させず、輪郭、形、動き、ラベルのうち複数で伝える。
- 既存の480×270の論理解像度と整数座標によるピクセル表現を、当面の基準とする。
- 画像化後も、選択枠、状態表示、デバッグ表示など動的な表現にはCanvasの図形描画を併用できるようにする。
- 保存データ、シミュレーション、進行条件には、表示改善だけを理由とした変更を加えない。

## 4. 実装順序

### Stage 0 — 現状基準と視覚ルールの準備

実装前に、初期状態と主要な進行状態の基準画面を決める。少なくとも初期フロア、採掘中、運搬中、エレベーター積載時、アップグレード後を対象とする。

併せて、背景、通路、操作対象、選択対象、警告、報酬に使う明度とアクセントの役割を定義する。この段階では素材を量産せず、後続判断の基準だけを作る。

完了条件：

- 比較に使う代表状態と画面サイズが決まっている。
- 操作可能、選択中、実行可能、停止中、詰まりの表示上の意味が整理されている。
- 変更前後を比較する確認項目が列挙されている。

### Stage 1 — 操作対象の識別基盤

最初に、画像素材へ依存しない操作性の基盤を整える。

- ポインター位置にある対象を判定し、対象上だけカーソルを変える。
- ホバー、選択、実行可能、実行不可を区別する表示を追加する。
- 必要時だけ対象名や簡単な状態を世界内に表示する。
- 見た目より少し広い論理ヒット領域を定義し、描画素材と分離する。
- マウス操作だけでなく、今後のキーボード選択やタッチ対応にも再利用できる対象モデルにする。

この段階は既存の図形描画で実施する。先に操作対象の意味と判定を安定させることで、後の画像差し替えによる操作性の後退を防ぐ。

#### 利用者に起きる変化

- 可視かつ選択可能な対象には、平常時から低コントラストの共通コーナーマークが表示される。
- マウスまたはペンが対象上にある間だけカーソルが変わり、明るいホバー枠と対象名、必要な場合は短い状態が対象付近に表示される。
- クリックまたはタップ後はホバーと同じ対象が選択され、持続する選択枠と既存のコンテキスト欄で詳細と操作を確認できる。
- 選択して確認できる対象は、主操作を実行できない間も対象として扱う。`BUSY`、`DEPLETED`、`NO WALKWAY`などの短い状態と、形の違いによって実行不可を伝える。
- 名称は原則としてホバー時だけ世界内に表示する。選択後の名称と詳細は既存のコンテキスト欄を正本とし、全対象への常設ラベルは追加しない。

#### 維持する不変条件

- クリック後に発生する移動、採掘、設備選択などの既存のゲーム操作を変えない。同じ鉱脈へ到着済みで採掘可能な場合に、再クリックで採掘する現在の操作も維持する。
- シミュレーション、進行条件、イベント、乱数、保存形式を変えない。ホバー状態と論理ヒット領域は保存しない。
- コンテキスト欄は選択対象に従い、ホバーだけでは切り替えない。
- 480×270の論理解像度と整数座標によるピクセル表現を維持する。
- ゲーム状態に存在しない対象や、未解放・未建設の対象を操作可能に見せない。
- 状態と無関係なアニメーション、常設HUD、Stage 2の次の一手の案内を追加しない。

#### 対象モデルと責務

操作対象の識別子、論理ヒット領域、強調表示領域、ラベル位置、表示名、短い状態、選択可否、主操作の実行可否、重なり優先度を、Canvas APIに依存しない一つの操作対象モデルから導出する。対象の描画外形や将来の画像の透明領域を、ヒット領域の正本にしない。

責務は次のように分ける。

- ゲーム状態：クリック後の選択対象と、既存の操作可否を決める。ホバーを持たない。
- 操作対象モデル：現在のゲーム状態から、可視対象と論理領域、表示用メタデータ、優先度を純粋に導出する。
- Runtime：ポインターの論理座標を一時的に保持し、ホバーとクリックを同じ対象解決関数へ渡す。対象が変わった時だけCanvasのカーソルを更新する。
- Renderer：全本体を描画した後の最前面レイヤーで、共通マーク、ホバー枠、選択枠、短いラベルを描く。
- React：クリック後のゲーム状態のpublishを受け、既存のコンテキスト欄を更新する。ポインター移動だけではReact snapshotを更新しない。

状態の流れは次のとおりとする。

```text
pointer move → 論理座標 → 操作対象モデル → hover表示 / cursor
click / tap  → 同じ論理座標と対象解決 → 既存Runtime操作 → selection
selection    → Canvas選択枠 + Reactコンテキスト欄
```

対象識別子は既存の選択対象と同じ意味を使う。ヒット領域や表示用メタデータは保存対象の型へ追加せず、表示・入力境界のモジュールに置く。描画位置と判定位置で共有すべき設備アンカーは共通定数または共通レイアウト関数から参照する。

#### 状態ごとの視覚表現

- 通常：低コントラストの小さなコーナーマーク。対象名は出さない。
- ホバー：明るい細いコーナー枠と対象名。対象が選択・確認可能なら、主操作が実行不可でもポインター用カーソルを使う。
- 選択中：ホバーより連続性のある持続枠。詳細と操作はコンテキスト欄に表示する。
- 実行可能：小さな塗りつぶしマークとアクセントを補助的に使う。
- 実行不可：斜線または中抜きマークと短い理由を使う。色の違いだけに依存しない。
- ホバーかつ選択中：選択枠の形を維持して明度を上げ、異なる意味の枠を重ねない。

世界内の短い状態は、操作可否または停止原因の理解に必要な場合だけ表示する。`MINE`、`SEND`のような次の操作そのものの案内はStage 2で扱う。

ラベルは対象の上を第一候補とし、画面端では内側へ寄せる。対象や重要な運搬物を覆う場合は下側へ退避する。同時に表示するhoverラベルは一つとし、選択中対象の詳細を重複表示しない。

#### 重なりと一時的な操作不可

重なり優先度はRendererの条件分岐順に依存させず、操作対象モデルへ明示する。具体的で小さい操作部を背後の大きい対象より優先し、同順位なら前面描画、さらに同じなら安定した対象順で決める。

- Bore Consoleは背後の鉱脈より優先する。
- Elevatorの操作盤と籠は同じElevator対象として扱う。
- Rail StopとCargo Hubは、重なった鉱脈より優先する。
- 同種の鉱脈が重なる場合はポインター中心に近い対象を優先し、同距離なら安定した配列順を使う。
- 枯渇中の鉱脈、Remote-only鉱脈、JAMMED設備、上昇・下降中の見えているElevatorは選択して状態を確認できる。実行できない操作は状態表示とコンテキスト欄の無効ボタンで示す。
- フロア間のElevator移動中は世界内対象を返さず、移動画面の背後をホバーまたは選択できないようにする。

#### 入力範囲

Stage 1ではマウスとペンのホバー、クリック、および既存のタップ選択を対象とする。タッチではホバーを前提にせず、タップ後の選択枠とコンテキスト欄で同じ情報を得られるようにする。

キーボードによる前後の対象選択、専用キー割り当て、タッチ専用レイアウトは実装しない。将来のキーボード選択に備え、対象モデルには安定した識別子、論理位置、安定した並び順を持たせる。既存のSpaceによる採掘は維持する。

#### 変更対象の候補

- `src/components/game/GameCanvas.tsx`：pointer move / leaveとタップをRuntimeへ渡す。
- `src/runtime/GameRuntime.ts`：保存しないポインター状態、共通の対象解決、カーソル更新を担当する。
- `src/render/interactionTargets.ts`（新規候補）：操作対象モデル、座標変換、hit判定、優先順位、表示用メタデータを純粋関数として定義する。
- `src/render/gameRenderer.ts`：分散した最終pickと、全対象の補助表示を統合する。
- `src/render/canvasRenderer.ts`、`src/render/phase5Renderer.ts`：個別のpick処理を共通モデルへ移し、既存本体描画を維持する。
- `src/render/entities.ts`、必要な設備描画関数：個別の選択枠を共通の最前面描画へ移す。描画アンカーは必要な範囲だけ共通化する。
- `src/game/types.ts`：既存の選択対象識別子を操作対象モデルから再利用できる形に整理する場合だけ変更する。保存形式は変更しない。
- `src/components/context/ContextPanel.tsx`と各Context：選択対象と実行不可理由の既存表示に不足がある場合だけ、短い状態文言を補う。
- `src/style.css`：Canvas全体の常時crosshairを廃止し、通常時と対象上のカーソルを分ける。

#### 依存関係を踏まえた実装順序

1. 初期状態、採掘中、運搬中、Elevator積載時、アップグレード後、および後半設備の代表画面をStage 0の比較基準として確定する。
2. 操作対象の識別子、座標変換、論理hit領域、優先順位を純粋な対象モデルへ集約し、既存clickの対象と結果が変わらないことを自動テストで固定する。
3. 各Rendererの`pickTarget`を共通解決へ置き換え、フロア間移動中と重なりの規則を適用する。この時点では視覚表現を変えない。
4. Runtimeへ保存しないポインター状態を追加し、pointer move / leave、対象上だけのカーソル変更、同じ解決結果を使うclick / tapを接続する。
5. 全本体描画後の共通補助レイヤーへ、通常、ホバー、選択、実行可否の表示を追加する。既存の個別選択枠は対象単位で置き換え、恒久的な二重描画を残さない。
6. 名称、短い状態、画面端と重なり時のラベル配置を追加し、コンテキスト欄に不足する実行不可理由だけを補う。
7. 自動回帰を通し、代表画面と実プレイで発見性、誤認、ラベル衝突、hit領域を確認する。

#### 各段階の完了条件

- 対象モデル集約：全可視対象について識別子、論理hit領域、優先度が一意に定まり、描画外形を変えずにhit領域を調整できる。
- click移行：既存の主要対象を同じ位置で選択でき、鉱脈の移動・再クリック採掘、設備のコンテキスト表示、Space採掘に回帰がない。
- hover接続：空白上では通常カーソル、対象上だけでポインター用カーソルとなり、hoverだけではゲーム状態、Runtime revision、Reactコンテキスト欄が変化しない。
- 視覚状態：通常、ホバー、選択、実行可能、実行不可を色以外の形または文言でも区別でき、後半設備を含む全対象で選択枠が表示される。
- 統合：ホバー中の対象をクリックまたはタップすると同じ対象が選択され、フロア間移動中は背後の対象を操作できない。

完了条件：

- 初見のテスト参加者が説明なしで鉱脈、作業台、エレベーターを指し示せる。
- ホバー対象とクリック後の選択対象が一致する。
- 素材の透明部分や外形に左右されず、主要対象を安定して選択できる。
- Archive、Research、Core Console、Crew Board、Rail Stop、Cargo Hub、Freight、Boreを含む既存の選択可能対象で、同じ状態表現の規則が使われている。
- 枯渇、Remote-only、JAMMED、Elevator移動などの実行不可または一時停止状態を、選択不能と混同しない。

#### 自動テスト

- CSS表示座標から480×270論理座標への変換と、hit領域の内外境界。
- 見た目より広い余白、動くElevatorの現在位置、非表示・未解放・未建設対象の除外。
- Boreと鉱脈、Rail Stopと鉱脈などの重なり優先度と、同順位の安定順。
- 枯渇、Remote-only、JAMMED、上昇・下降、フロア間移動中の選択可否と実行可否。
- hoverとclickが同じ対象解決を使い、空白clickが既存selectionを変えないこと。
- hoverだけではゲーム状態、保存対象、Runtime revision、ContextPanelが変化しないこと。
- D-001での鉱脈選択、移動、再クリックまたはSpace採掘の既存経路。
- E2Eで対象上だけのカーソル、hoverと選択の一致、タップ後のコンテキスト表示を確認する。後半設備はRail Stop、Cargo Hub、Boreから少なくとも一つ代表経路を含める。

#### 人手確認

- D-001で説明なしに鉱脈、作業台、Elevatorを発見できるか。
- 初期状態、採掘中、運搬中、Elevator積載時、アップグレード後で、補助表示がゲーム状態と矛盾しないか。
- D-030 / D-060 / D-100の端末、D-180のCrew Board、D-250のRail Stop / Cargo Hub / Freight、D-400の歩行可能鉱脈 / Remote-only鉱脈 / Boreを識別できるか。
- 通常、ホバー、選択、実行可能、実行不可を、色を手掛かりから外しても区別できるか。
- ラベルが画面外へはみ出さず、対象、運搬物、状態表示を覆いすぎないか。
- 代表的な表示幅で論理hit領域が過小または過大でなく、隣接対象の誤選択が増えないか。
- マウス、ペン、タップの各経路で、選択後に同じコンテキスト情報へ到達できるか。

#### 今回対応しない事項

- キーボードによる対象巡回選択、専用ショートカット、Canvas対象ごとのDOMアクセシビリティ要素。
- タッチ専用レイアウト、モバイル向けの画面再構成、長押しやジェスチャー。
- 次の一手を教えるチュートリアル、操作文言、理解済み状態の保存。
- 新しい操作対象、設備、ゲームルール、進行条件、演出、音響の追加。
- 画像素材の導入、既存図形本体の作り直し、Stage 2以降の詳細設計。

#### Stage 3への引き継ぎ

- 画像の外形、透明余白、アニメーションフレームが変わっても、Stage 1の論理hit領域と対象識別子を維持する。
- 各画像素材は操作対象モデルと同じ意味上のアンカーを使い、素材ごとの透明ピクセルから判定領域を生成しない。
- 共通の補助レイヤーを画像本体より後に描き、コーナーマーク、ホバー枠、選択枠、状態ラベルを図形描画として継続利用できるようにする。
- 画像化で本体の占有領域が大きく変わる場合も、先に画像へhit領域を合わせず、人手確認で操作性を評価して論理領域を明示的に改訂する。

### Stage 2 — 次の一手の案内

中長期目標とは別に、初回プレイの手動物流を一手ずつ案内する。

- 鉱脈の選択
- 移動
- 採掘
- 回収と帰還
- エレベーターへの積載
- 地上への発送

案内は常設説明文ではなく、対象付近の短い表示とコンテキスト操作欄を中心にする。一度理解した操作は繰り返し強調せず、既存セーブや周回プレイを妨げない終了条件を持たせる。

完了条件：

- 新規プレイヤーが外部説明なしで最初のScrap獲得まで到達できる。
- 案内表示と実際に受け付ける操作が一致する。
- 周回時や自動化後に初回案内が不要に再表示されない。

### Stage 3 — 階調整理と画像描画の縦切り導入

ここで画像素材への移行を開始する。操作対象と案内の仕様が決まる前に画像を量産すると、輪郭、余白、状態差分を作り直す可能性が高いため、Stage 1〜2より後に行う。一方、エフェクトを先に作ると新しい画像の接地点や大きさに合わせた再調整が必要になるため、Stage 4〜5より前に導入する。

この縦切りでは、現行図形をそのままPNG化するのではなく、既存の配置と操作契約を保ちながらD-001の画作りを全面刷新する。テラリアは横視点での人物の読みやすさ、装備レイヤー、状態シルエットの参考に留め、画素、人物造形、配色、装備デザインはLOOP SHAFT固有のものにする。

#### 対象場面

初回手動配送だけでなく、次の代表状態を対象にする。

- 新規開始時の待機と最初の鉱脈選択。
- 鉱脈への移動、採掘待機、スイング、損傷、枯渇、回収。
- Cargoを持った帰還、Elevator待ち、積み込み、積載後の選択と発送。
- 装備アップグレード後のプレイヤーと作業台。
- Porter、Crew、Engineer、床Cargo、後半設備が存在する進行後のD-001。
- 一部または全部の素材が読み込み中、もしくは読み込みに失敗した状態。

#### 今回画像化する対象

- D-001の岩盤基底、坑道の奥壁と空洞、支柱、梁、レール、床。
- 地上施設と中央シャフトの静的構造。
- プレイヤー本体とRusty / Steel Pickaxe、Boots、Packの外観差分。
- Scrap Ledge、Copper Pocket、Fossil Crackの3鉱脈。
- 作業台。
- Central Elevatorの籠、扉、前面フレーム、および`EMPTY_SHAFT`用の狭幅差分。

#### 今回は図形描画を維持する対象

- Stage 1の通常マーク、hover、selection、実行可否、論理hit領域。
- Stage 2の次の一手案内と初回配送通知。
- Elevatorケーブルなど、長さや位置が連続的に変わる部分。
- 地面、所持中、Elevator内、床上のCargoと容量表示。

画像化した本体と図形版の本体は通常時に二重描画しない。既存図形は対象単位のfallbackとしてだけ残し、素材が利用可能になった対象から画像を正本に切り替える。

#### 描画レイヤー

Rendererクラスの呼び出し順ではなく、意味上のレイヤーを次の順序で明示する。

1. void色。
2. 背景岩盤。
3. 坑道奥壁、地上施設、中央シャフト後面。
4. 床、梁、レール。
5. 鉱脈、作業台後面、Elevator後面。
6. プレイヤー、Porter、Crew、Engineer。
7. 地面、所持中、籠内、床上のCargo。
8. Elevator前面、扉、設備前景。
9. 状態灯、容量、採掘破片などの動的表示。
10. Stage 1のinteraction overlay。
11. Stage 2のinitial guide。
12. 配送、発見、獲得などの最前面通知。

D-001は暖かい土、錆、木材、琥珀色の灯りを基調とする。背景、坑道構造、操作対象、character、cargo、案内の順に明度と色差を上げ、青緑は自動化と後続深度の識別色として温存する。背景を単純に明るくせず、操作対象と運搬物を輪郭と階調で分離する。

#### 素材形式、寸法、anchor

- runtime素材は透過PNGとし、1素材ピクセルを1論理ピクセルとして整数座標へ描画する。
- 半透明の輪郭は原則使わず、Canvasの補間を無効のまま維持する。
- 背景は一枚絵へ設備を焼き込まず、岩盤、坑道、構造物、床、シャフト、地上施設の交換可能な層に分ける。配置ずれを避けるため、D-001の背景層は原則480×270の透明レイヤーで揃える。
- ファイル名は小文字のkebab-caseとし、状態名はコード上の意味状態と対応させる。
- プレイヤーのフレームセルは40×40、見える人物本体は約18×30、足元anchorはセル内`(20, 38)`を基準とする。世界上の足元は現在の`character.x`と`character.y + 8`へ合わせる。
- 鉱脈のフレームセルは48×40、anchorは下中央`(24, 40)`とし、既存の強調領域へ収まる外形を基準とする。
- 作業台は基台と展示装備を分離し、Tool、Boots、Packの独立した組み合わせを全パターン一枚ずつ作らない。
- Elevatorのフレームセルは56×44、anchorは籠中心`(28, 20)`とし、現在の`elevatorY(state)`へ追従させる。籠後面、Cargo、前面と扉を分ける。
- 画像の透明ピクセル、書き出し余白、フレームごとの外形を論理hit領域や対象anchorの正本にしない。

#### プレイヤーの状態差分

プレイヤーは本体、ヘルメット、Tool、Pack、Bootsを同じフレーム格子で合成できる構成にする。左右は原則として右向き素材のCanvas反転で共有する。

| 意味状態 | フレーム数 |
| --- | ---: |
| 待機 `idle` | 2 |
| 歩行 `walk` | 4 |
| 採掘待機 `mine-ready` | 2 |
| 採掘スイング `mine-swing` | 8 |
| 回収 `collect` | 4 |
| 積載歩行 `carry-walk` | 4 |
| 積載待機 `carry-idle` | 2 |
| Elevatorへの積み込み `load` | 4 |

採掘スイングは既存の0.44秒とhit時点へ同期させ、岩HPが減る時点と画像のヒットフレームを一致させる。待機と歩行は対応するGameStateの間だけ循環し、状態と無関係に再生しない。フレーム番号は保存しない。

#### 画像状態を選ぶ責務

Simulationや保存型へ表示専用状態を追加しない。GameStateから意味上の描画状態を純粋に導出し、素材キー、clip、frame、facing、anchorをRendererへ渡す。

```text
IDLE                    → idle
MOVING_TO_NODE          → walk
MINING + swingなし      → mine-ready
MINING + swingあり      → mine-swing
COLLECTING              → collect
RETURNING               → carry-walk
WAITING_FOR_ELEVATOR    → carry-idle
LOADING                 → load
```

採掘、回収、積み込みは既存の進捗時間へ同期し、待機と歩行だけRenderer時刻で対応clipを循環する。鉱脈は現在の75%・40%のHP境界を使い、`full`、`damaged`、`critical`、`depleted`を選ぶ。Elevatorは`IDLE_BOTTOM`と`LOADING`で開扉、`ASCENDING`と`DESCENDING`で閉扉を選ぶ。

#### 生成プロンプトと素材原本

画像生成を始める前に、全素材、全状態、論理寸法、anchor、フレーム数を一度洗い出して固定する。生成途中に対象ごとの即興プロンプトを追加しない。

固定する生成仕様には次を含める。

- マスタープロンプトとネガティブ条件。
- 基準照明、D-001の階調役割、固定パレット。
- 素材一覧、論理寸法、anchor、clip、フレーム数、出力先。
- 使用した生成モデルと版、基準画像、プロンプトのハッシュ。
- 横視点、低解像度pixel art、暖色の土・錆・木材・琥珀灯、明確なシルエット、硬いpixel edgeを共通条件とする。
- 文字、UI、過剰発光、neon主体、gradient、既存ゲーム素材やキャラクターの模倣を除外する。

最初に人物、鉱脈、設備、背景の基準シートを生成して一組を選定し、その基準シートを画像参照として全状態差分を生成する。テキストプロンプトだけに同一人物や装備比率の維持を任せない。選定した生成元、生成仕様、runtime用書き出しを区別して管理し、不採用の試行画像を無制限にリポジトリへ蓄積しない。

#### パレットと後処理

素材ごとに独立したk-meansを実行しない。基準シート群から固定seedで候補色を抽出し、人手でD-001共通パレットを確定した後は、固定パレットへの最近傍量子化だけを行う。

- 完全透明ピクセルを色抽出から除外する。
- nearest-neighborで縮小する。
- 透過境界の色滲み、1px孤立点、フレーム間の接地点ずれを検査する。
- 背景用低明度色、操作対象用中明度色、character用中高明度色、cargoと案内用高明度色を同じパレット内で役割分担する。
- 後処理は再現可能なscriptにし、手作業だけをruntime素材の生成条件にしない。

#### 読み込み、キャッシュ、fallback

- D-001素材をCanvas接続時に非同期preloadし、完了をゲーム開始条件にしない。
- URL単位で`loading`、`ready`、`error`をキャッシュする。
- `ready`の対象だけ画像を描き、`loading`と`error`ではその対象の既存図形を描く。
- 一つの素材の失敗で、他の画像化済み対象まで一括fallbackさせない。
- 読み込み失敗は同じURLについて一度だけ記録し、ゲーム内の常設警告や保存状態を増やさない。
- Assetの状態をGameStateや保存データへ入れない。

#### Stage 1・2との統合

- `InteractionTarget`の対象ID、論理hit形状、hit優先順位、stable order、selectionとの対応を変えない。
- 画像本体は既存の強調領域へ収め、interaction overlayを画像より後に描く。
- Elevatorの籠と固定操作盤を同じ対象として扱う現在の仕様を維持する。
- 鉱脈、作業台、Elevatorの論理anchorを維持する。
- 大型化した人物と案内が重ならないよう、character向けStage 2案内だけは素材の上端から明示的に導出する。透明外形からは導出しない。
- Elevator本体内の点滅`SEND`文字はStage 2案内と重複するため削除候補とし、ContextPanelの`SEND`操作、状態灯、積載表示を残す。

#### 自動テストと比較画像

- 全asset key、論理寸法、anchor、source rectがmanifestとatlas内で整合すること。
- 全CharacterState、Swing進捗、鉱脈HP境界、Elevator状態が一意の画像状態へ解決されること。
- `loading`、`ready`、`error`と、対象単位のfallback。
- Stage 1の対象ID、hit形状、優先順位、hoverとclick / tapの一致。
- 同じ鉱脈の再click / tap、Space、`MINE`、Elevator選択後の`SEND`。
- hoverだけではGameState、Runtime revision、ContextPanelが変わらないこと。
- 新規開始、選択、移動、採掘、鉱脈損傷・枯渇、回収、帰還、積み込み、発送、装備強化、Porter、Crew、Engineer、後半設備、読み込み中、部分的な読み込み失敗の固定状態で比較画像を取得する。
- 比較画像は固定viewportとdevice scaleで取得し、通常表示に加えてgrayscaleでも層ごとの明度差を確認する。

#### 人手確認

- 初回配送を外部説明なしで完了できるか。
- 待機、歩行、採掘、回収、運搬、積み込みを静止画と動作中の両方で区別できるか。
- 生成フレーム間で人物の顔、体格、装備、接地点が揺れないか。
- hit位置、hover、selectionが画像の対象と一致するか。
- Stage 1の枠とStage 2の案内が背景へ埋もれず、対象やCargoを覆いすぎないか。
- 進行後のD-001で画像化済みプレイヤーと図形のPorter、Crew、Engineer、後半設備の縮尺差が許容範囲か。
- 読み込み中や失敗時にも対象、状態、Cargo、操作経路が消えないか。

完了条件：

- 読み込み中と部分的または全面的な読み込み失敗でも、操作対象、状態表示、Cargo、既存操作経路が消えない。
- 素材一覧、固定プロンプト、基準画像、パレット、命名、anchor、後処理、追加手順が再利用可能な正本として管理されている。
- Simulation、イベント、乱数、経済、保存形式へ変更を加えていない。
- 画像化した本体と図形版本体を通常経路で二重描画していない。

### Stage 4 — 主要対象の画像化とシルエット改善

縦切りで決めた方式を、主要な設備、鉱脈、人物、運搬物へ広げる。単なる高精細化ではなく、縮小表示でも役割を判別できる外形を優先する。

- 鉱脈：不規則で自然な外形と、種類ごとの特徴
- 作業台：横長の天板と工具
- エレベーター：縦長の籠、扉、積載空間
- 端末：画面または状態灯
- 運搬設備：直線、レール、反復構造
- プレイヤーと作業員：役割、向き、積載状態を判別できる形と配色
- 鉱石・特殊品：通常品と希少品を大きさ、輪郭、補助演出で区別
- 地表設備、岩盤、坑道、床：深度ごとの基調を保った背景層

全深度で共通する機能物を先に画像化し、続いて現在存在する各深度の背景と固有設備へ展開する。新しい大型ランドマークや、現在のゲーム状態に存在しない装飾物の追加は今回の完了条件に含めない。

完了条件：

- 主要対象を色だけでなく輪郭でも区別できる。
- キャラクターの待機、移動、採掘、運搬状態が読み取れる。
- アップグレードや設備解放が世界内の画像差分として現れる。
- 現在実装済みの各深度について、背景と固有設備が画像素材中心で描画される。
- 表示中のアニメーションが実際のゲーム状態と一致する。

### Stage 5 — 行動結果のフィードバック

画像化した対象の位置と大きさが固まった後、ゲームイベントに結び付く短い演出を追加する。

- 採掘：衝撃、破片、鉱脈の損傷
- ドロップ：生成位置と希少度の認識
- 回収：鉱石からバッグへの移動
- 搬入：バッグからエレベーターまたは物流設備への移動
- 地上到着：換金・Data・Core獲得の通知
- 購入・建設：設備の外観変化と作業完了表示
- 停止・詰まり：原因箇所の状態表示

演出は、シミュレーション結果を受けて再生する。演出終了をゲーム進行の条件にはせず、描画負荷や設定により省略しても結果が変わらない構成とする。

音響も同じイベントへ対応させるが、連続採掘や自動物流で過密にならない優先度と再生制限を持たせる。

完了条件：

- 採掘物が生成され、運ばれ、換金される流れを数値なしでも概ね追える。
- 重要な成功、停止、詰まりを画面から判別できる。
- エフェクトや音を減らしてもゲーム状態と操作結果は変わらない。

### Stage 6 — HUDの情報階層整理

世界内表示とフィードバックが揃った後、重複しているHUD情報を整理する。HUDを先に削ると、世界側に代替表示がない期間が生じるため、この順序とする。

- Scrap、Data、Coreは主要資源として優先表示する。
- Carry、Lift、各バッファは数値だけでなく容量表示を検討する。
- 研究、貨物、作業員などは状態変化や異常時を優先して表示する。
- 未解放で当面操作できない項目は、必要になるまで弱めるか隠す。
- 現在の一手と中長期目標を混在させない。
- 世界内で十分に伝わる情報を常時HUDから外す。

完了条件：

- 初期画面で現在資源、積載状況、次の目的を短時間で確認できる。
- HUDを見続けなくても、主要な作業と物流の状態を把握できる。
- 情報量が増える後半でも、警告と現在の判断材料が埋もれない。

### Stage 7 — 統合確認と残課題の切り分け

最後に、開始直後から自動化後までを通して確認し、今回の範囲で直す問題と、モバイル対応、深度ランドマーク、追加コンテンツなど次期作業を分離する。

完了条件：

- 新規プレイヤーが最初の換金まで迷わず到達できる。
- 手作業から自動化への変化が、世界内の人物・設備・物流の変化として見える。
- 代表的な画面サイズで文字と主要対象が判別できる。
- 既存のゲーム進行、保存、決定論的シミュレーションに回帰がない。
- 残る改善点が、今回の未達か次期範囲かに分類されている。

## 5. 画像素材移行の考え方

### 移行時期

画像素材の本格導入はStage 3で開始し、Stage 4で主要対象へ展開する。理由は以下の通り。

- Stage 1で操作状態とヒット領域を先に定義できる。
- Stage 2で案内に必要な余白、ラベル位置、強調対象を把握できる。
- Stage 3で階調ルールと実素材を同時に評価できる。
- Stage 5のエフェクトを最終的な対象位置へ合わせられる。
- Stage 6で、世界内表示に移せた情報を確認してからHUDを減らせる。

### 段階的な置き換え

1. D-001の背景と主要4対象で方式を検証する。
2. 共通キャラクター、鉱脈、設備、運搬物を置き換える。
3. アップグレード・稼働・停止・損傷など状態差分を追加する。
4. 現在実装済みの各深度の背景と固有設備へ共通方式を展開する。
5. 新しい大型ランドマークや追加の情景演出は別計画で追加する。

図形描画は一括削除しない。選択枠、容量、経路、警告など画像より動的描画が適する部分は残す。一方、同じ本体を画像と図形の両方で恒久的に描く状態は避け、対象単位で正本を切り替える。

### 素材作成時に決める項目

Stage 3の縦切りでは、次をD-001用の生成仕様として画像生成前に固定する。

- 素材一覧、基準ピクセル密度、論理寸法、対象ごとの占有領域、anchor。
- GameStateと対応するclip、フレーム数、既存進捗との同期点。
- 左右反転で共有する素材と、通常幅・狭幅など個別に描く素材。
- 本体、装備、Cargo、状態灯のうち、画像レイヤーとCanvas図形のどちらで合成するか。
- 背景の個別PNGと、人物・設備のsprite atlasおよびmanifestの構成。
- 固定マスタープロンプト、基準画像、D-001共通パレット、再現可能な後処理。
- 読み込み、URL単位のキャッシュ、対象単位のfallback。
- 生成仕様、選定した原本、runtime用書き出し物の管理場所と生成モデルの記録。

Stage 4以降は、Stage 3で確定した形式を既定値として使う。ただし、深度固有の景観、対象の占有領域、状態差分は実画面比較を経て追加し、D-001の色や寸法を全対象へ機械的に固定しない。

## 6. 検証方針

各Stageでは、その段階で変えた判断だけを検証する。

- 操作性：対象発見率、誤クリック、最初の換金までの停止箇所
- 視認性：背景と対象の分離、状態差分、文字サイズ、色以外の手掛かり
- 因果関係：採掘、回収、搬入、搬送、地上到着を追えるか
- 回帰：シミュレーション、保存、進行条件、既存の主要E2E
- 性能：画像読み込み後の初回表示、アニメーション中の描画安定性

自動テストは状態と操作経路の回帰に使い、見やすさ、雰囲気、手応えは代表画面の比較と人によるプレイ確認で判断する。

## 7. 実装着手時に詰める事項

- チュートリアルの保存単位と再表示方法
- キーボードでの対象選択を今回含めるか
- エフェクトの上限数と簡略表示設定
- HUDの最終レイアウトと用語
- 色覚差、低コントラスト環境、画面拡大への対応水準
- 深度固有ランドマークを次期作業としてどの順で追加するか

これらは該当Stageの開始時に、直前Stageの実画面とプレイ結果を根拠に決定する。

Stage 3については、固定プロンプトと基準画像を使った生成支援、D-001共通パレットによる後処理、Renderer外のAsset loaderとmanifest、対象単位の図形fallbackを採用することを決定済みとする。具体的なプロンプト本文、全素材一覧、寸法、anchorは、画像を生成する前に一組の生成仕様として確定する。
